Workshop 3 — Firmware and basic mechanical design (PCB housing)

The slides: Workshop 3: getting things made. Nobody learns a CAD program (computer-aided design: the program a part is drawn in) today: Claude Code writes the geometry; you specify, look, check the numbers, slice and decide.

  • Setup check — your laptop with VS Code and Claude Code, OpenSCAD and Bambu Studio installed and opened once, the class repository up to date, your dev board and a USB-C data cable.
  • Getting things made: the fabrication menu — two ways to a part: make it here (FDM printing on the Bambu P1S, the laser cutter, hand tools) or order it (CNC machining, sheet metal, resin and metal printing, EDM); typical times, costs and tolerances.
  • Tips to make 3D prints and cut parts turn out right — layer direction and the 45° rule, walls and tolerances, nuts in pockets, materials, the slicer, the laser.
  • From an idea to a file — design the way it will be made; the files (STEP, STL/3MF, DXF); the five CAD programs compared; reading OpenSCAD (a part as a short program of shapes, moves and combinations); the AI design loop: specify, generate, look, measure, slice, test.
  • The housing — we build it together in OpenSCAD with Claude Code, in eight steps: specify · answer Claude's questions · generate · look · check the numbers · fix and make it yours · export and slice · the test coupon and your files.
  • Pulling the course together — Project 3 is your instrument: the firmware and the app that use the class board, in your housing; your first firmware driver and app panel in sim mode; a great project website that shows what the app does, how to use it and what it can do (one repository, one website, one card); the presentation; the option of a video the AI renders for you.

Firmware and app — a driver and its panel

The block-driver interface

Every driver is a folder firmware/src/blocks/<section>_<name>/ implementing name() / begin() / loop() / handle(cmd, reply) / status(out). You start from blocks/template/.

The protocol

WebSocket (a live two-way connection between the phone page and the board) messages {block, cmd, args} in and {block, status} out; one panel module per driver in host/pwa/panels/<section>.js; instrument.py (a Python program on your PC) mirrors the same commands in Python.

Sim mode

The SIM flag fakes the hardware so the whole app runs on a bare dev board — you work ahead of the boards and swap the flag off when they arrive.

One alarm rule per panel

A driver's status → the base alarm engine → a module output + notification: A "AI1 above a threshold" or "no free induction decay seen" · B "output clipped" or "TRIG edge seen" · C "opto count jumped" or "a module output left on".

E11: driver + panel in sim. Choose the part of the board your instrument needs first — the section you worked on in Workshop 2 is a natural start, not an obligation. /tutor L3: copy the template to blocks/<section>_<name>/; fill in the section's commands (A read_all, set_range, capture · B set_dc, sine, pulse, dio · C module, module_all, opto_reset); make the SIM branch return plausible values; add the panel and one alarm rule; flash (write the firmware onto the board over USB); see the panel react on the phone; open the pull request (a request to merge your changes into the shared project; someone reviews it first). The tutor generates the skeleton; you name the commands, write the SIM values, and explain one message round-trip before flashing. Sections that talk to each other are paired (B ↔ A for a waveform measured on an input, B ↔ C for a pulse that switches a module output). Done when the panel controls the section in sim and the pull request is open.

Housing — part of Project 3

Tips for printed and cut parts

Nuts in pockets are the fastening: an M3 nut slides into a 5.8 mm hexagonal pocket, 2.5 mm deep, and the screw pulls it tight. Walls 2 mm; holes +0.3 mm (printed holes come out small); layers are the weak direction, so let the load run along them; 45° is the steepest overhang that prints without support. Print a test coupon first: it answers the fit for your printer. The PCB front panel is the face of the instrument, so the front cover is a plate with holes where the panel's parts are.

Your own design

You write the specification yourself, from the housing brief: what the housing must hold, the printing rules, the files to hand in, and the two board models. Those models, hardware/release/class-board.stl and front-panel.stl (STEP versions beside them), were exported from the final KiCad boards with kicad-cli, keeping only the connectors, LEDs and modules, so every dimension comes from the boards and none from a ruler. Ask Claude to ask you its questions before it writes code. Start by opening each board on its own in OpenSCAD, one import() line at a time, and looking at it; there is no example housing to copy, because the design is yours.

Output

housing.scad, base.stl, cover.stl, coupon.stl (STL: the 3D-print file), cover.dxf (DXF: the laser-cutting drawing) and a screenshot, in docs/students/<name>/housing/, by the cutoff. The institute prints and cuts them.

E12: your housing. On the shared screen, and in your own Claude Code session with OpenSCAD beside it: write your specification from the brief, answer Claude's questions, let it write housing.scad, look at it and check the numbers in the console, fix it and make it yours, export the parts and slice them in Bambu Studio, add the test coupon, commit from Source Control. A design in another CAD program you already use is welcome too, if it fits the boards and meets the deadline. Done when the files are in your folder.
